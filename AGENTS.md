# AGENTS.md — wch-mouse

Bare-metal firmware for a wireless gaming mouse and its 2.4G receiver dongle on the **WCH CH585** (RISC-V RV32IMC + Zba/Zbb/Zbc/Zbs/Xw). There is no host build, no test suite, and no CI — verification is a cross-compile plus on-hardware flashing.

## Build & flash

One CMake project builds both firmwares — the mouse (root `src/`) and the 2.4G dongle (`dongle/`) — from a shared vendor SDK/HAL/link setup in `cmake/wch_sdk.cmake`. The WCH/MounRiver GCC toolchain (`riscv32-wch-elf-`) is mandatory; a plain `cmake -B build` fails by design (`CMakeLists.txt` FATAL_ERRORs without a toolchain file).

```sh
cmake --preset wch            # toolchain file + binaryDir build/
cmake --build build           # both -> build/wch-mouse.* and build/dongle/wch-dongle.*
cmake --build build --target wch-mouse     # or just one
cmake --build build --target wch-dongle
```

- One preset (`wch` -> `build/`); the dongle is always RF.
- Toolchain discovery order: `$WCH_TOOLCHAIN_ROOT` -> `/opt/wch/riscv-wch-gcc15` -> `~/MounRiver/...`. Override with `-DWCH_TOOLCHAIN_ROOT=/path`.
- `compile_commands.json` is a **symlink to `build/`** and `.clangd` reads `build/`; run the configure step before expecting LSP/clangd to work on `src/`.
- Flashing uses external tools and is **not** part of the default build. The mouse owns the unsuffixed names, the dongle's are suffixed `-dongle`:
  - `cmake --build build --target flash-usb` / `flash-usb-dongle` — `wchisp -u flash`
  - `cmake --build build --target flash-serial` / `flash-serial-dongle` — `wchisp -s flash`
  - `cmake --build build --target flash-mrs` / `flash-mrs-dongle` — MounRiver `libmcuupdate.so` via `scripts/mrs_flash.py`; works even when the two-wire debug interface is closed. Needs `WCH_COMMUNICATION_LIB_DIR` or auto-discovery.
- The mouse can reach the ROM ISP bootloader **without a power cycle**: hold the BOOT strap (PB22) for 3 s while USB is attached (`src/app/isp.c`). The ROM picks ISP over the application by checking whether CodeFlash starts with a program, so this erases block 0 and resets — the firmware does not survive and a download must follow, but the DataFlash record (radio mode, settings) does. Gated on VBUS so a press on battery cannot wipe the image. The dongle has no button and sits in a case, so it takes the same request over USB — the one channel the case still exposes: a vendor Feature SET whose payload starts with the magic `WCHISP!` (`dongle/src/isp.c`, `dongle/src/rf_dongle.c`), sent with `scripts/mouse_proto.py --dongle isp`. The handler runs in the USB ISR, so it only raises a flag; the erase/reset runs from the main loop in `isp_poll()`.

- Configuration options:
  - `WCH_BLE_ENABLE` — BLE peripheral transport.
  - `WCH_RF_ENABLE` — 2.4G RF transport; shares the single radio with BLE.
  - `WCH_DCDC_ENABLE` — internal DC-DC; requires the 10 µH inductor between VSW and VDCID, OFF for boards that strap VSW to VDCID.
  - `WCH_DEBUG_UART=1` — printf retarget UART 0–3.
  - `WCH_LOG_LEVEL=LOG_LVL_DEBUG` — log verbosity.

## Layout & boundaries

- `src/` — mouse application code (edit here), grouped by role: `app/` (mouse, air_mouse, radio_mode, bat, motor, bio) · `transport/` (the transport router + USB/BLE/RF backends, plus the shared `rf_cfg.h` on-air contract) · `sensor/` (PAW3395 and the vendored Bosch BMI270/BMI2 API with its ports) · `display/` (the I2C bus, the SSD1315 OLED and its vendored LibDriver core) · `led/` (WS2812 driver + `rgb_fx` animations) · `bsp/` (vendor-derived USB device/descriptors, UART and logging). Headers are included by basename, so each group sits on the include path rather than being path-qualified in the sources.
- `dongle/` — the 2.4G receiver dongle firmware: `src/main.c` superloop, `src/rf_dongle.c` RF host (RX) → USB HID.
- `cmake/wch_sdk.cmake` — source lists, flags and the `wch_firmware*()` helpers shared by both firmwares. Add a driver once, both get it.
- `StdPeriphDriver/`, `Startup/`, `RVMSIS/`, `Ld/Link.ld` — vendor SDK. Do not edit; formatting is disabled there to preserve WCH style.
- `ble/` — vendor-forked BLE HAL + GATT profiles + prebuilt closed-source libs (`libCH58xBLE_PERI.a` peripheral-only; full `libCH58xBLE.a` kept as fallback). Only `src/transport_ble.c` is ours.
- `docs/` — datasheets + `io.csv` pin map (tracked). `docs/CH585EVT/` (75 MB vendor SDK) is **gitignored/local-only**. `ble/` is stored as UTF-8 while the vendor copies under `docs/CH585EVT` are GBK, so raw diffs show comment-encoding noise; `ble/Profile/` also differs from the vendor `HID_Mouse/Profile/` by the HID report map in `hidmouseservice.c` and logging in `hiddev.c`.
- New mouse `.c` files go in `APP_SOURCES` (root `CMakeLists.txt`), dongle ones in `dongle/CMakeLists.txt`; vendor and shared sources live in `cmake/wch_sdk.cmake`. All lists are explicit, there is no glob.
- Linker: FLASH 448K @ 0x0, RAM 128K @ 0x20000000; custom `Ld/Link.ld`, no CRT/libc (`-nostartfiles`, `nano.specs` + `nosys.specs`). C99, soft-float.

## Architecture

- Entry point: `src/main.c` bare-metal superloop.
- **Transport router** (`src/transport.c`/`.h`): an array of `transport_t` backends; the first whose `link_up()` is true wins, order USB > RF > BLE. Backends: `transport_usb.c`, `transport_rf.c` (`WCH_RF_ENABLE`), `transport_ble.c` (`WCH_BLE_ENABLE`); both radio files always compile and stub out when their define is absent. Add new backends to `s_backends[]`.
- **Configuration** (`src/app/proto.c`): a vendor HID Feature report (usage page 0xFF00, 63 data bytes), with `proto_handle_set/get` called only by the USB device layer. A direct session therefore needs the cable — USB is independent of the radio mode and wins the transport router, so this still works while running RF. The same report also goes to the **dongle**, which has no protocol module of its own: it captures the frame (`dongle/src/rf_dongle.c`) and rotates it through the RF replies, and the mouse reassembles and runs it from `rf_poll()` (thread context — a SET can block ~50 ms, so it must never run in the ISR). SET and GET commands thus both work wirelessly in RF mode. The answer travels back in the mouse's own frames and the dongle holds the last whole one to serve a `GET_FEATURE` on (see the reverse channel below). Host side: `scripts/mouse_proto.py --dongle` (PID 0xFE0D), which polls until a reply matching its own command and sequence byte turns up — the window is longer than the USB path's because a command can block the mouse (the panel bring-up alone NACKs for ~120 ms). The udev rule must cover **both** product ids.
- **2.4G RF link**: `src/transport/rf_cfg.h` is the contract shared by both firmwares — mouse = device/TX (`src/transport/transport_rf.c`), dongle = host/RX (`dongle/src/rf_dongle.c`). The RFIP `rfPackage_t.length` byte is the **total frame length including the 4-byte header**, not the payload length; treating it as the payload sends a truncated frame whose tail the receiver reads as stale DMA memory.
- **RF reverse channel**: the dongle answers every packet it receives with a short `RfAck_t` (type `0x7E`) carrying its own received count, and the mouse switches to RX after each send to catch it. Differencing that count against its own TX count is what makes air loss visible. The reply also carries the host's pending SET command in `RF_CMD_CHUNK` pieces; the mouse restarts its assembly on every chunk 0, which is the retry, and `cmd_id` is what stops a repeat from executing twice. The mouse's own frames carry the answer back the same way (`RfPacket_t.resp_id`/`chunk`/`reply`), streamed as `RF_REPLY_PASSES` passes of the same 63-byte frame; the dongle reassembles it, snapshots the first whole pass so a later torn one cannot destroy it, and serves that snapshot to `GET_FEATURE`. A new host command invalidates the snapshot and ignores the re-sends still in flight, so a read-back can never hand out the previous request's answer. This is a software ping-pong, **not** a hardware ACK (the RFIP exposes no way to load an ACK payload); a missed reply costs nothing because the next `rf_poll()` send re-arms TX, which is the property that stops a bad window from stranding the radio.
- **Radio mode** (`src/radio_mode.c`): the CH585 has one radio, so the mouse runs RF **or** BLE and picks at **boot** — not live (`RFRole_SwitchMode` exists but has no example and needs an idle radio). The mode lives in DataFlash at `0x00070000` and defaults to RF. **Hold side 1 (back) and the wheel click together for 3 s, then release** to store the other mode and `SYS_ResetExecute()` into it. USB is independent of the mode and always wins the transport router.
- **Mouse report**: 6-byte packed `MouseReport_t` (`src/mouse.h`), the same logical layout over USB and BLE. The layout is duplicated in the USB HID descriptor (`src/usb_desc.c`, `MyMouseReportDesc`) and the BLE report map (`ble/Profile/hidmouseservice.c`) — keep both in sync. **USB framing adds a Report ID**: the USB report descriptor has two top-level collections (mouse + vendor Feature) and Windows refuses to start such a device without Report IDs, so every USB report is led by its ID byte — mouse `0x01` makes the USB input report 7 bytes and the Feature `0x02` makes control transfers 64 bytes. BLE still sends the bare 6-byte report. Note the stale `4-byte report` comment in `usb_desc.c`: dx/dy are actually 16-bit.
- Sensors: PAW3395 (SPI) in `paw3395.c`; its motion burst is read on the MOTION pin's **PA7** falling edge through SPI0's DMA (`paw3395_motion_*` in `paw3395_port.c`). BMI270 via the vendored Bosch BMI2 API (`bmi270.c`/`bmi2.c`). Pin assignments: `docs/io.csv`.
- Logging: `src/log.c` non-blocking ring over UART1; use `LOG_E/W/I/D(tag, ...)`. `LOG_LEVEL` strips higher-verbosity messages at preprocess time. `log_printf` blocks on the UART FIFO — thread context only, never from an ISR.
- **BIO health module** (`src/app/bio.c`, external module on UART3): reset is a GPIO on **PA11** (active low); `bio_init()`/`bio_reset()` bring it up. Mode commands are single bytes on the UART3 link — acquisition `0x8A`/`0x88`, sleep `0x98`/`0x00`, checkup `0x8E`/`0x8C` — and the checkup duration is a 3-byte `0x84` frame. Its 88-byte real-time packets (delimited by a lone `0xFF` header) are parsed locally by `bio_rt_feed()` from the UART3 ISR, in parallel with the USB CDC bridge; `main` shows the **last valid** packet on the OLED. UART3 RX therefore stays enabled without a host, and only the CDC forwarding is gated on USB. On the UART side note the module's own JFC103 protocol: 38400 8N1, little-endian.

## Power management

`HAL_SLEEP = FALSE` in `ble/HAL/include/CONFIG.h`, so there is no RTOS idle and the core otherwise runs at 62.4 MHz with the 1 kHz TIM3 tick and the superloop flat out. The only sleep is the explicit standby path below; everything else is per-peripheral gating on top of it. There is no power harness in the repo: a baseline has to come from bench instrumentation (current meter / power analyser), measured per state (idle on the desk, moving, BLE vs RF, USB attached).

**Standby** (`src/app/power.c`) — after `POWER_IDLE_MS` (30 s) with no activity the peripherals are parked and the core enters `LowPower_Sleep` (2.6 µA; RAM32K + RAM96K kept). It runs only when **not** tethered, **not** in air-mouse mode and on **RF** — BLE cannot deep-sleep, its link is kept alive by connection events and the stack cannot be rebuilt from there. `power_poll()` returns true on the pass that wakes, which is how `main` re-arms TIM3/TIM2/UART3 and rebuilds the radio; nothing on that path may execute from flash once the flash is down, hence `__HIGH_CODE`, and the flash needs a few hundred µs after waking before it can be read. Wake sources are PA7 (motion), the GPIOB button inputs plus encoder A (armed only around sleep; `GPIOB_IRQHandler` in `mouse.c` records the edge and runs from RAM) and VBAT (cable/charger) — no RTC wake. PB19 cannot wake: the GPIOB interrupt mask is 16 bits, so only PB0–PB15 qualify.

Gated:
- **USBHS PHY** — `usb_poll()` powers it while USB owns the link, and also whenever the radio is **not** BLE: RF mode keeps it hot so a host attached to the cable can take the link over at once, which is why a charger in RF mode leaves it drawing 10–20 mA. BLE mode instead uses the 800 ms VBUS-edge probe (see the USB gotcha) and leaves it off. Either way it is only ever on with VBUS present, so on battery it costs nothing; 10–20 mA is still the largest saving so far.
- **IMU** — `bmi270_port_init()` only loads the config; both sensors stay disabled until `air_mouse` enables the gyro on entry, so nothing reads the IMU in normal use.
- **PAW3395** — read on the MOTION pin's PA7 falling edge through SPI0 DMA, so an idle scan never touches SPI0.
- **DC-DC** — `WCH_DCDC_ENABLE` drops run current to ~60% of the pass-through LDO (needs the VSW inductor).
- **Panel / LED rail / BIO** — the biggest standing loads, so all three run only while the cable is in: tethered means there is no battery to protect. `settings_apply_peripherals()` is the one place that decides, re-run at boot, on a VBUS change and on any config change. `periph_batt` (protocol `SET_PERIPH 0x61`) lifts the gate so the user's own `oled`/`bio`/`rgb` switches decide. Standby is unaffected: `standby_park()` cuts all three before sleeping and `standby_restore()` re-applies the cable/`periph_batt` policy on wake, so an idle mouse still sleeps with the peripherals on. The BIO module's own draw is still not characterised.
- **Motor** — only pulsed on an air-mouse switch, so no steady load.

- **RGB transients escape the gate**: `rgb_fx`'s `transient` path (the boot announce, an air-mouse toggle, the armed switch combo) powers the rail for its window even when `enable` is false, so a mode switch is still visible on battery. It blinks at `RGB_FX_DIM` (16) — brightness 1 is indistinguishable from off on a WS2812.

Battery: BQ24075 (PGOOD PB6 / CHG PB5, both open-drain active low) and `BT_VOL` (PA3 = ADC AIN6, VBAT through a 1:2 divider → `bat_voltage_mv()`); `bat_poll()` samples it.

## Gotchas that will bite

- The 1 kHz tick runs on **TIM3**, leaving **TIM0 free for the RF transport**. TIM3 is safe only because the BLE HAL hijacks `TMR3_IRQHandler` solely when `RF_8K` is defined — which this build does not use (RF 4k max). Enabling the 8k RF mode would silently steal TIM3 and freeze the tick. TIM1 is the RGB WS2812 DMA and TIM2 is the UART/CDC timeout; SysTick is the HAL's RF-8k clock.
- `TMOS_SystemProcess()` (625 µs cadence) must be pumped from the main loop; calling it from an ISR corrupts the scheduler.
- USB readiness: `bat_power_good()` only means VBUS is present (a dumb charger passes it), and `USBHS_DevEnumStatus` is never cleared on unplug. `usb_ready()` in `transport_usb.c` clears device state itself when VBUS drops — do not "simplify" it. The USBHS PHY costs 10–20 mA, so `usb_poll()` gates it: on whenever USB owns the link or no BLE link exists, off while BLE is active (with an 800 ms VBUS-edge probe so a newly attached host can still enumerate and take over).
- BLE motion is accumulated in `transport_ble.c`: notifications are paced to the connection interval, and rejected reports must be merged (they carry relative motion) rather than dropped.
- BLE HID only reports over a **bonded, encrypted** link: `HidDev_Report()` gates on `hidDevConnSecure` and the report CCCD is `GATT_PERMIT_ENCRYPT_WRITE`, so the host must pair first. On Linux BlueZ, `bluetoothctl connect` alone is not enough — run `agent on` / `default-agent`, then `pair`, then `trust`. We use `GAPBOND_PAIRING_MODE_INITIATE` and a static device address (`GAP_ConfigDeviceAddr(ADDRTYPE_STATIC, ...)`) so the peripheral drives pairing and the host keeps recognising its bond across reboots.
- Duplicate IRQ symbols are expected: the PERI library provides strong `Ecall_M/U_Mode_Handler` / `LLE_IRQHandler`, while `Startup/startup_CH585.S` declares weak stubs that the library overrides.
- RF TX buffer: `RFIP_SetTxParm()` hands the DMA a pointer and returns, so the buffer it points at must not be mutated afterwards. `transport_rf.c` therefore keeps the motion accumulator (`s_acc`) separate from the DMA buffer (`s_tx`) — merging them corrupts the packet mid-flight.
- **RF RX DMA buffer**: point `rxDMA` at `RF_RX_BUF_LEN` (264) bytes, **not** at a buffer sized for the frame. The vendor example documents that minimum, and `rxMaxLen` is the *frame length*, not the buffer size — the two are independent. Sizing the reply buffer to its 6 bytes let the DMA run past the end; the tail landed in the TX buffer and the cursor drifted steadily in one direction. Silent until it hits something live.
- **I2C / OLED**: the CH585 I2C defaults to **PB13/PB12, which are this board's USB HS pins** — `i2c_bus_init()` sets `RB_PIN_I2C` to move `SCL_/SDA_` to **PB21/PB20** (docs/io.csv). SDA/SCL carry **external 4.7 kΩ pull-ups to 3.3 V** and the bus runs at 400 kHz with no retries; a board without those pull-ups only has the CH585's internal 20–50 kΩ, whose ~9 µs rise time barely fits even 100 kHz, so drop `I2C_CLOCK_HZ` and raise `I2C_RETRIES` there. The address step must go through `I2C_CheckEvent`: the peripheral only clears `ADDR` when STAR1 *and* STAR2 are read, and `I2C_GetFlagStatus` reads just one — leave it set and the write path never reaches TXE.
- **SSD1315 panel**: `src/display/ssd1315/` is vendored LibDriver (MIT) and `ssd1315_port.c` is the CH585 side of it, mirroring how `sensor/` pairs `bmi270.c` with `bmi270_port.c`. Two traps: LibDriver passes the **8-bit** I2C address (0x78) while `i2c_bus` takes **7-bit**, so the port shifts; and the controller **NACKs every command for ~120 ms after reset is released** until its oscillator and charge pump settle, so the port delays there — without it the panel looks absent. `oled_flush()` drives a page per I2C transaction rather than byte-by-byte, which is ~10x faster on this bus.
- A single-radio build deliberately ignores the DataFlash mode byte (`RADIO_MODE_SELECTABLE`): a stale value written by a dual-radio image must not disable the only backend an RF-only or BLE-only image carries. The switch is triggered by `mouse.c` from the debounced buttons and lands on release, so PB22 is no longer involved at all — the old footgun where a held BOOT strap sent the mode-switch reset into the ISP bootloader is gone.
- `EEPROM_READ/WRITE/ERASE` address the DataFlash by **offset** (0 = `0x00070000`), not by the absolute address the memory map shows; passing the absolute address makes the ROM reject the whole command (`EVT/EXAM/FLASH` writes at offset 0). `src/radio_mode.c` stores its record at offset `0x0000` — the vendor's BLE SNV is at `0x7000` and the IAP image flag at `0x6000`, so they do not collide. Buffers must be RAM, 4-byte aligned.
- **PAW3395 motion read is interrupt-driven and shares SPI0 with every sensor write**: a PA7 falling edge (MOTION is active low; it is also wired to PB17, but only PA7 can raise a GPIO interrupt) runs `paw3395_motion_burst()` — command + `SPI0_MasterDMARecv()` — and accumulates into a delta pair that `mouse_scan()` drains with `paw3395_motion_read()`. The blocking configuration writes (`paw3395_init`, `set_cpi`, `set_mode`, `set_lift_cut`) use that same bus, so call `paw3395_motion_stop()` before them and `paw3395_motion_start()` after; `air_mouse.c` does this around its shutdown and re-init. Keep the read synchronous inside the ISR — a hand-rolled async DMA completion path read corrupt data and made the cursor race one way.
